# guandao 惯导例程评估与移植建议

本文总结 `ai/guandao` 下几个惯性导航相关例程，目标是判断哪些内容适合当前 TC387 智能车项目复用。当前项目已有轮速编码器、IMU963RA、GPS、SD 日志、绝对转向编码器，因此惯导方案应优先服务于实车闭环和数据记录，而不是直接移植完整三维 SINS/EKF。

## 总体结论

最适合当前车的路线是：短周期用编码器里程 + IMU 航向做二维航迹推算，低频 GPS 只做原点/位置校正，固定赛道场景再加入按里程记录/回放航向的功能。

不建议现阶段直接移植完整 PSINS、Python `starlight` 或 GPS/INS 21 状态松组合。这些代码理论完整，但依赖矩阵库、双精度、大量参数标定和可靠 IMU/GNSS 观测，移植成本高，调参成本也高。当前更应该先把“稳定、可解释、可记录”的二维惯导跑通。

## navigation-master

路径：`ai/guandao/navigation-master`

关键文件：

- `TC系列核心文件，方便移植/navigation.c`
- `TC系列核心文件，方便移植/navigation.h`
- `TC系列核心文件，方便移植/kalman.c`
- `TC系列核心文件，方便移植/flash.c`

这个例程更像智能车实战代码，不是通用三维惯导。它的核心是按固定里程间隔采样航向角，把赛道航向存入 Flash，之后按同样里程回放参考航向，并输出当前航向和记录航向的偏差。

好的部分：

- 按里程触发，而不是按时间触发。对智能车更合理，因为速度变化时，按时间记录会导致空间采样不均匀，按里程记录能让路径索引对应赛道位置。
- 航向角用 `angle_Z = 360 * Dirchange + yaw` 做连续化，避免 `-180/180` 跳变导致控制误差突然变大。
- 用整数保存 `yaw * 100`，避免 Flash 里直接存浮点，思路适合嵌入式。
- 记录和回放分离，状态机简单，便于在任务模式里控制“学习一圈”和“复现一圈”。
- 用左右编码器平均作为里程来源，符合双后轮/双编码器车的基本里程计模型。

主要问题：

- 代码和具体工程强耦合，直接依赖 `CarSpeed.speed_L`、`CarSpeed.speed_R`、`angle_Z`、`flash_union_buffer` 等全局变量。
- `Nag_Set_mileage` 是编码器计数，不是米，移植时必须换算成明确单位，否则换轮径/编码器分辨率后难维护。
- Flash 页管理写死，且边界保护比较粗糙，不适合直接接入当前工程。
- `Nag_Prev` 前瞻数组没有真正形成完整前瞻控制逻辑。
- 只处理航向偏差，不直接输出二维位置，也不解决 IMU 长时间漂移。

对当前项目的建议：

- 值得复用“按固定距离采样航向、按固定距离回放参考航向”的思想。
- 不要直接复制 `navigation.c`，应改成独立模块，例如 `nav_path_record.c/.h`，输入为 `distance_delta_m` 和 `yaw_deg_continuous`，输出为 `ref_yaw_deg`、`yaw_error_deg`、`finished`。
- 存储层先不强绑 Flash，可先用 RAM + SD CSV 调试，确认有效后再考虑 Flash 持久化。

## navigation-master 的 kalman.c

文件名叫 `kalman.c`，但主要内容是 AHRS 姿态解算，不是标准 Kalman 滤波。

好的部分：

- 上电静止采样 100 次估计陀螺零偏，这是实车必须做的。
- 加速度做一阶低通，能降低姿态解算抖动。
- 四元数更新姿态，避免欧拉角积分的奇异性和耦合问题。
- 用重力方向误差反馈校正 gyro，结构接近 Mahony AHRS，适合 MCU 实时运行。
- yaw 连续化处理值得保留，智能车控制更需要连续航向而不是限制在 `[-180, 180]`。

主要问题：

- `delta_T` 写死为 `0.0025f`，如果中断频率不严格等于 400 Hz，姿态会系统性漂移。
- 陀螺和加速度量程比例写死为 `16.4f`、`8/4096`，只适配特定 IMU 配置。
- `fast_sqrt()` 实际返回的是快速倒平方根近似，命名容易误导。
- 四元数更新里先做了一次欧拉积分，随后又做带二阶修正的更新，存在重复积分风险，建议重写为清晰的单次更新。
- 缺少加速度模长有效性判断。车辆急加速、震动、碰撞时，重力校正会把线加速度误认为姿态误差。

对当前项目的建议：

- 如果当前 IMU963RA 库已经能稳定输出 Pitch/Roll/Yaw，先不要替换整套 AHRS。
- 可以借鉴“陀螺零偏初始化、yaw 连续化、加速度有效性门限”。
- 若后续重写 IMU 解算，应使用实际 `dt`，不要写死周期。

## navigation-main

路径：`ai/guandao/navigation-main`

这是 MATLAB 捷联惯导算法集合，更偏教学和算法验证。重点文件包括 `insupdate.m`、`cnscl.m`、`kfupdate.m`、`static_alignment.m`、`demo_SINS.m`。

好的部分：

- `insupdate.m` 是标准捷联惯导更新流程：圆锥/划桨补偿、地球参数、速度更新、位置更新、姿态更新，注释清楚。
- `cnscl.m` 给出了 2 到 6 子样圆锥/划桨误差补偿系数，适合高频 IMU 或高动态场景参考。
- `kfupdate.m` 把 Kalman 时间更新、量测更新、协方差对称化写得很清晰，适合作为滤波器模板。
- 工程中明确区分角增量 `wm`、速度增量 `vm`、姿态 `qbn`、速度 `vn`、位置 `pos`，变量含义比很多嵌入式例程严谨。

主要问题：

- MATLAB 代码不能直接移植到 TC387，需要重写矩阵、向量和存储结构。
- 完整三维惯导依赖高质量 IMU 和稳定初始化，低成本车载 IMU 单独积分位置会很快漂。
- 地球自转、经纬高、重力模型对小车短距离二维运动不是第一优先级。

对当前项目的建议：

- 用它作为“正确算法参考”，不要作为直接移植代码。
- 当前车只需要二维平面：`x/y/yaw/speed`，可以暂时忽略地球自转和高度通道。
- `kfupdate.m` 的结构可以借鉴到后续 GPS/编码器融合，但状态量应简化，例如 `[x, y, yaw, speed, gyro_bias]` 或更小。

## GPS-INS-master

路径：`ai/guandao/GPS-INS-master`

包含粗对准、精对准、纯惯导和松组合。它比 `navigation-main` 更接近 C/C++ 实现，但仍是离线/半离线 GNSS/INS 示例。

好的部分：

- `1_粗对准/StaticAlig.m` 用重力矢量和地球自转矢量求初始姿态，理论完整。
- `2_精对准/Alig.m` 用 7 状态 Kalman 通过速度误差修正失准角，展示了精对准的基本结构。
- `3_纯惯导/pureINS_c_plus/ins.cpp` 有四元数、姿态矩阵、重力、地球参数和惯导更新 C++ 实现。
- `4_松组合/process.cpp` 明确建立了状态转移矩阵、观测矩阵、Q/R/P 参数，展示 GPS 位置观测修正 INS 的松组合流程。
- 参数初始化比较完整，包括 ARW、VRW、gyro bias、acc bias、相关时间等。

主要问题：

- 使用 `double` 和动态矩阵，嵌入 TC387 后资源占用和调试复杂度都会增加。
- 默认场景是 GNSS/INS 离线数据或高质量导航数据，不是智能车短距离高震动场景。
- 精对准依赖较长静止时间和地球自转观测，低成本 MEMS IMU 在智能车上效果有限。
- 松组合状态较多，Q/R 参数如果没有标定，实际表现可能比简单互补融合更差。

对当前项目的建议：

- 借鉴参数分层：传感器噪声、初值方差、观测噪声要集中配置，不要散落在控制代码里。
- 借鉴 GPS 低频修正 INS 的结构，但先做简单位置重置或一阶融合，不要一上来做 21 状态滤波。
- 对小车来说，GPS 更新频率低、室外漂移大，GPS 更适合作为路线/位置参考，不适合作为高速闭环唯一依据。

## inertial-navigation-code-master

路径：`ai/guandao/inertial-navigation-code-master`

重点是 `psins_cpp_lite/psins_lite`，它是 PSINS 风格的 C++ 简化实现，包含 `PSINS.cpp/.h`、`KFApp.cpp/.h`。

好的部分：

- `CSINS`、`CIMU`、`CEarth`、`CKalman`、`CSINSGNSS` 分层清楚，是比较成熟的导航软件架构。
- `CKFApp` 使用 15 状态误差模型：姿态误差、速度误差、位置误差、陀螺零偏、加计零偏。
- 有反馈校正 `Feedback()`，不是只估计误差而不回灌主导航状态。
- 有量测屏蔽、量测丢失计时、协方差上下限、渐消/自适应 R 等工程保护。
- 有时分更新 `TDUpdate()`，能把大矩阵更新分摊到多个周期，适合实时系统思想。

主要问题：

- C++ 类体系和矩阵库很大，直接移植到当前 C 工程不划算。
- 依赖双精度和较多内存，TC387 能跑但调试成本高。
- 对传感器标定、坐标系、初始姿态、噪声参数要求高，否则结果不一定可靠。
- 当前智能车的主要需求是二维路径、航向和速度控制，用完整 PSINS 会过度复杂。

对当前项目的建议：

- 把它作为长期参考架构，不作为当前直接移植对象。
- 可以学习它的“主导航状态 + 误差状态滤波 + 反馈修正”结构，未来做高级 GPS/INS 融合时再引入。
- 当前更适合先做轻量状态，例如二维 `x/y/yaw/speed`，必要时加 `gyro_z_bias`。

## starlight-main

路径：`ai/guandao/starlight-main`

这是 Python GNSS/INS 实验框架，重点文件是 `starlight/module/ins.py`、`starlight/module/ins_error.py` 和 `starlight/algo/*`。

好的部分：

- 数据结构清楚，把 IMU 原始数据、增量、PVA、误差状态分开。
- `ins.py` 明确区分角速度/加速度输入和角增量/速度增量，适合分析数据流。
- `ins_error.py` 建立了 15 维误差状态，包含位置、速度、姿态、gyro bias、acc bias。
- 示例脚本体现了 IMU 高频预测、GPS 低频校正的典型流程。
- 适合用 PC 离线验证算法、调参数、画图分析。

主要问题：

- 依赖 Python、NumPy、SciPy、pyins，不可能直接放到 TC387 上运行。
- 模型复杂度和当前车载硬件/控制任务不匹配。
- 代码里部分注释和坐标转换仍处于实验状态，不建议直接当最终算法依据。

对当前项目的建议：

- 用作离线工具参考：未来可以把 SD 卡日志导出到 Python 里分析轨迹和误差。
- 不用于嵌入式移植。
- 它的模块边界值得借鉴：输入数据、积分器、误差滤波器、分析器要分开。

## BMI088_INS-master

路径：`ai/guandao/BMI088_INS-master`

这是 STM32H7 + BMI088 的驱动/测试工程，不是完整惯导算法工程。

好的部分：

- IMU 初始化流程严谨：上电等待、SPI 模式唤醒、软复位、读 chip id、自检、逐项配置、读回校验。
- 把寄存器表、默认配置、移植层分开，结构清楚。
- 使用 DWT 做高精度时间测量，对 IMU 采样周期验证有价值。
- 对每个配置项设置错误码，便于定位初始化失败原因。

主要问题：

- 硬件是 BMI088 + STM32 HAL，和当前 IMU963RA + TC387 BSP 不一致。
- 主要是驱动质量参考，不提供可直接用于当前车的惯导状态估计。

对当前项目的建议：

- 可借鉴“写寄存器后读回校验”和“精确测量 IMU 周期”。
- 不直接移植驱动。

## 当前工程 code/nav 的问题与改进方向

当前工程路径：`TC387_kd1 pid/code/nav`

已有结构是合理的：`nav_gps` 负责 GPS 到局部坐标，`nav_ins` 负责惯性/里程推算，`nav_fusion` 负责融合状态，`nav_control` 提供上层接口。

目前需要注意的问题：

- `nav_ins_update_with_accel()` 当前一旦使用加速度，就主要按加速度积分位移，编码器位移只用于初始化。这对低成本 IMU 很容易漂，实车更应该以编码器位移为主。
- 编码器计数是 `int16`，长期运行会回绕，里程差应显式按 16 位环形差值处理。
- 位移积分最好使用前后航向的中值，而不是只用当前航向，转弯时误差更小。
- GPS 校正不应每次生硬覆盖 INS 状态，至少应提供可调融合系数；调试阶段可以先覆盖，但控制阶段更建议渐进修正。
- 缺少路径记录/回放模块，而 `navigation-master` 的这部分正适合智能车固定赛道。

推荐后续整合顺序：

1. 先修正 `nav_ins`：编码器为主、加速度只辅助速度估计、处理计数回绕、使用航向中点积分。
2. 增加 `nav_path`：按固定距离记录连续航向，回放时输出参考航向和航向误差，先 RAM 实现，后续再接 Flash/SD。
3. 增加日志字段：记录 `nav_x/y/yaw/speed`、`path_ref_yaw`、`path_yaw_error`、GPS valid、INS valid。
4. 再考虑轻量融合：GPS 位置用一阶融合修正 INS，而不是直接上 15/21 状态 EKF。
5. 最后才考虑误差状态滤波，状态量建议从 `[x, y, yaw, speed, gyro_bias]` 开始，不要一开始全量 PSINS。

## 适合直接吸收的“好东西”

- 按里程采样路径，而不是按时间采样。
- yaw 连续化，内部使用连续角，输出控制误差时再 wrap 到 `[-180, 180]`。
- IMU 上电静止零偏估计。
- 加速度低通和有效性门限，避免大动态时错误修正姿态。
- Kalman 更新后协方差强制对称化。
- 观测有效性判断和丢失保护，避免 GPS/IMU 瞬间坏数据污染状态。
- 导航状态、传感器输入、融合逻辑、路径记录逻辑分层，不互相直接依赖硬件全局变量。

## 不建议直接照搬的部分

- 完整三维 SINS 的地球模型和高度通道，当前智能车短距离二维运动收益不高。
- 大型 C++ 矩阵库和 15/21 状态 EKF，当前调试成本大于收益。
- 写死 IMU 周期、量程比例、Flash 页号和工程全局变量。
- 直接用加速度二次积分算车体位移。低成本 IMU 和震动环境下漂移会非常快。
- 把 GPS 作为实时闭环主反馈。GPS 更新慢且有跳变，更适合低频校正和日志验证。

## 对当前车的建议方案

短期可落地版本：

- 主状态：`x_m, y_m, yaw_deg, speed_mps, distance_m`。
- 输入：左右编码器累计计数、IMU yaw、IMU gyro_z、可选前向加速度、GPS 低频位置。
- 位移：左右编码器增量平均得到 `delta_s`。
- 方向：IMU yaw 提供航向，内部连续化，积分位置时使用上一次 yaw 和当前 yaw 的中值。
- 速度：编码器速度为主，加速度只做短时平滑，不直接决定位置。
- GPS：无 GPS 时纯里程/IMU；有 GPS 时按可调系数慢慢拉回位置。
- 固定赛道：加入 `nav_path` 记录/回放航向，输出 `yaw_error_deg = current_yaw - ref_yaw`。

这条路线比直接移植完整 GNSS/INS 更可靠，也更容易通过 SD 日志验证每一步是否正确。
